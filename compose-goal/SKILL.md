## Что делаю

Помогаю пользователю (или агенту) составить /goal по правилам команды. Превращаю расплывчатые запросы в чёткий контракт с проверяемым стоп-условием.

## Когда меня вызывать

- Пользователь хочет написать или улучшить /goal
- Пользователь говорит "помоги превратить в /goal: ..."
- Пользователь даёт расплывчатую задачу, которая требует долгой самостоятельной сессии агента
- Пользователь спрашивает "как правильно писать goal?"

## Когда использовать /goal, а когда нет

Используй только если выполнены ВСЕ три условия:

1. Задача — это >30 минут механической работы (миграция, подъём покрытия, фикс по контрактным тестам, рефакторинг с тестами)
2. Есть **проверяемый стоп-критерий** (тесты зелёные, coverage ≥ X, сборка проходит)
3. Репозиторий готов: рабочая сборка, есть тесты, есть AGENTS.md

Плохие кандидаты: исследовательская работа, расплывчатое "сделай лучше", задачи без определения "готово", операции с прод-кредами, разрушительные действия в общей инфраструктуре. Если задача не подходит — скажи прямо и предложи обычный чат, а не /goal.

## Шаблон goal

При составлении goal следуй шаблону — одна строка на элемент, markdown-блок, без префикса `/goal` (его добавляет пользователь в композере):

```
**Objective:** <желаемое конечное состояние, одно предложение>
**Read first:** <файлы/PLAN.md/issue, которые прочитать перед стартом>
**Constraints:** <что нельзя ломать, регрессировать, трогать>
**Use:** <какие файлы/инструменты/данные разрешены>
**Validate:** <точная команда> after each change
**Between iterations:** <как выбирать следующее действие, что логировать>
**Document:** <пиши краткую документацию на каждое изменение — новые .md или правка существующих>
**Stop when:** <проверяемое условие>, OR when дальнейшие изменения требуют решения человека
```

### Элементы контракта

1. **Objective** — одно предложение, один конкретный результат. Цель должна быть **checkable** — чёткое "что считать успехом".
2. **Read first** — что прочитать до начала работы: файлы, PLAN.md, issue.
3. **Constraints** — что нельзя ломать, регрессировать, трогать: публичный API, файлы, конвенции. Это про **безопасность**.
4. **Use (Boundaries)** — разрешённая территория: файлы, инструменты, API, ресурсы. Если не указать — агент может начать рефакторить всю кодовую базу.
5. **Validate** — точная команда, которая докажет прогресс (`pytest -q`, `pnpm test`, `curl endpoint && check status`), и указание запускать её **после каждого изменения**. Проверка должна быть **автоматизируемой**.
6. **Between iterations (Iteration policy)** — как выбирать следующее действие после каждой попытки: "записывай что изменил, какой был результат, какая следующая гипотеза". **Экономит токены**.
7. **Document** — обязательная строка: пиши краткую документацию на каждое изменение — новые .md или точечные правки существующих.
8. **Stop when** — проверяемое условие успеха ИЛИ условие остановки из-за блокировки: "если повторяется одно и то же препятствие 3 итерации подряд — остановись, приложи список попыток, результаты и что именно заблокировало". **Предотвращает бесконечный цикл**.

## Правила

1. **Цель должна быть checkable** — агенту нужно чёткое "что считать успехом". Не "сделай хорошо", а "метрика X < 100ms".
2. **Проверка должна быть автоматизируемой** — команда, тест, скрипт. Не "убедись глазами", а `npm test` или `curl endpoint && check status`.
3. **Запрети reward-hacking явно**: "Не удаляй, не ослабляй и не сужай тесты ради прохождения цели." Иначе агент сжульничает со стоп-условием.
4. **Запрети scope creep явно**: "Не рефакторь несвязанный код. Не добавляй зависимости."
5. **Один objective, один stop condition.** Не превращай goal в бэклог задач.
6. **Лимит длины** — держи objective компактным (~4000 символов максимум). Детали выноси в файл (PLAN.md / GOAL_BRIEF.md) и дай ссылку в "Read first".
7. **Используй литеральные строки** для путей, команд, номеров issue — без обобщений.
8. **Говори агенту когда паузиться**: "Если <условие> — остановись и спроси разрешения перед продолжением."
9. **Iteration policy экономит токены** — вместо того чтобы каждый раз думать "что делать дальше", агент следует стратегии.
10. **Blocked condition предотвращает бесконечный цикл** — без него агент может бесконечно пытаться одно и то же.
11. **Не смешивай /goal с обычным чатом** — goal для долгих самостоятельных сессий, а не для вопросов-ответов.
12. **Короткие расплывчатые цели жгут токены** без пользы — лучше обычный промпт.

## Примеры

### Плохой Goal
```
/goal Починить падающий тест checkout
```

### Хороший Goal (починка теста)
```
**Objective:** Починить flaky тест checkout, чтобы он стабильно проходил 10 запусков подряд.
**Read first:** tests/checkout.test.ts, src/checkout/, AGENTS.md
**Constraints:** не менять API checkout, не трогать другие тесты.
**Use:** только src/checkout/, tests/checkout.test.ts.
**Validate:** `pytest -q tests/checkout.test.ts -x` after each change.
**Between iterations:** записывай что поменял, результат прогона, следующую гипотезу.
**Document:** добавь комментарий с причиной фикса, если в ней есть подводный камень.
**Stop when:** 10 зелёных прогонов подряд, OR когда не удалось воспроизвести проблему и нужен человеческий ввод.
```

### Хороший Goal (подъём покрытия)
```
**Objective:** Поднять покрытие в src/auth/ с ~38% до ≥75%.
**Read first:** src/auth/, tests/auth/, AGENTS.md
**Constraints:** не менять прод-код без необходимости для тестируемости, не добавлять зависимости.
**Use:** только src/auth/ и tests/auth/, стиль тестов — как в существующих.
**Validate:** `pytest --cov=src/auth --cov-report=term-missing` after each change.
**Between iterations:** записывай дельту покрытия после каждого чекпоинта.
**Document:** обнови раздел покрытия в README, если он есть.
**Stop when:** покрытие ≥75% и все тесты зелёные, OR когда непокрытый код требует дизайн-изменений.
```

## Meta-prompting (самый сильный приём)

Рукописные цели недо-специфицированы. Дай **второй сессии агента** (с загруженной кодовой базой) задание: (1) изучить репозиторий, (2) выявить скрытые допущения, ограничения, краевые случаи, (3) выдать готовый контракт по шаблону выше. Вставь результат в /goal. Качество прогонов на порядок выше.

## Self-goal setting

Агент может сам написать себе goal. Вместо ручного составления контракта дай ему намерение и сырьё (файлы для чтения, ограничения, команду валидации) и скажи: "Изучи репозиторий, затем напиши себе /goal с проверяемым стоп-условием и выполняй его. Если намерение неоднозначно — задай уточняющие вопросы перед стартом." Это meta-prompting, сделанный инлайн.

## Управление запущенным goal

| Ситуация | Действие |
|---|---|
| Проверить статус | Пользователь: `/goal` (или `/goal status`) |
| Поставить/заменить | Пользователь: `/goal <контракт>` |
| Мелкий дрейф | Просто напиши поправку в композере — goal авто-паузится и учтёт её |
| Расплывчатый objective | `/goal pause`, посмотреть статус, затем `/goal <уточнённая версия>` — не накапливай инструкции поверх размытой цели |
| Полная катастрофа | `/goal clear`, `git status` / `git stash`, пересобрать цель с meta-prompting и перезапустить |

Не давай дрейфующему goal работать "посмотрим, куда придёт" — токены горят, диффы растут.

## Операционные советы

- **Всегда ревьюй дифф перед мержем** — чем дольше автономия, тем больше кода надо проверять, а не меньше.
- **Первый запуск** — бери задачу на ~30 минут, чтобы понять, как goal реально останавливается, прежде чем доверять ему на ночь.
- **Политику запекай в AGENTS.md** — стандартную команду валидации, требование адверсариального само-ревью перед "готово", дополнительную QA-проверку даже при зелёных тестах. Тогда каждый goal наследует её без повторения в тексте.

## Процесс работы

1. Выслушай что пользователь хочет получить в goal
2. Если задача неочевидна — задай уточняющие вопросы
3. Проверь, подходит ли задача под критерии из секции "Когда использовать"
4. Составь goal по шаблону — markdown-блок, одна строка на элемент
5. Покажи пользователю готовый goal и спроси, всё ли подходит
6. По запросу отрефакторь / примени правки
