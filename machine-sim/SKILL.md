# machine-sim

Два разных вопроса — два разных инструмента. Не смешивать.

| Вопрос | Инструмент | Что доказывает |
|---|---|---|
| «Станок может исполнить программу?» | LinuxCNC + HAL + vismach | лимиты, оси, safety, порядок движений |
| «Деталь сядет и удержится?» | MuJoCo | контакты, трение, усадка, силы |

Общее правило: **числа только из одного источника** (`params.py`). G-код, MJCF и
проверки генерируются из него; координат «по месту» быть не должно.

## 1. LinuxCNC-прогон (кинематика)

### Запуск без GUI

```bash
halrun -U >/dev/null 2>&1            # снять остатки прошлой сессии
pkill -f rtapi_app
Xvfb :71 -screen 0 1280x1024x24 &     # свой дисплей, не xvfb-run
DISPLAY=:71 linuxcnc machine.ini program.ngc &
```

- `pkill -f "<строка>"` убивает **собственную оболочку**, если шаблон совпал с
  командной строкой. Заключай в скобки: `pkill -f "linuxcnc pr15_sim[.]ini"`.
- `halrun -U` и `pkill rtapi_app` — обязательны, иначе новый HAL не поднимется.
- Xvfb нужен свой (`:NN` + `DISPLAY=:NN`): `xvfb-run` не даёт управлять окнами
  и не подходит, когда нужен скриншот 3D-вида.

### HAL-пины и кнопки

- `halcmd setp` **не работает** на пине, подключённом к сигналу (`net`). Если
  панель жмёт кнопки, нужен userspace-компонент «оператор»: скрипты ставят
  `machine-safety.script-*`, а компонент сводит их с `halui`.
- Сброс E-stop — отдельное осознанное действие: сначала перезапустить watchdog
  (`enable-in 0 → 1`), потом `script-reset`.
- Пин вида `motion.digital-out-00` — это M-код, а не HAL-кнопка. Лог программы
  может быть пустым: диагностику пиши в свой файл, а не в stdout.

### Главная ловушка G-кода: M64 против M62

| Код | Когда срабатывает |
|---|---|
| `M62 P0` / `M63 P0` | **синхронно с движением**: выход меняется, когда станок доехал |
| `M64 P0` / `M65 P0` | **немедленно**, как только интерпретатор прочитал строку |

Интерпретатор читает программу с опережением. С `M64` «взять деталь» срабатывает,
пока станок ещё едет вниз, — захват закрывается в воздухе, а на отпускании деталь
падает не туда. Ошибки при этом кратны не времени, а шагу программы (легко
спутать с «взял не ту деталь из стопки»). Вывод: **для захвата/отпускания —
только `M62/M63`**.

### vismach (3D-вид)

- `Capture()`-точки обязаны быть в дереве модели, иначе `main()` падает на
  `invert()` пустой матрицы.
- Сбой в `traverse()` GUI проглатывает молча. Оборачивай в `try/except` и пиши
  `traceback` в файл (`/tmp/..._error.txt`), иначе видишь только «не собралось».
- Сцену собирай из одного источника боксов (`geom.py`), а не из чисел в скрипте:
  иначе вид, план и проверки разъедутся.
- Результат пиши **на каждое** изменение состояния, а не в конце: при падении
  иначе не видно, где остановилось.
- Состояние по выборке HAL-пинов приблизительно: частота обновления вида может
  быть 1–10 Гц. Для честной посадки используй пассивный захват (деталь садится
  в чашку в пределах конверта), а не «поймал момент».

### Программа обрывается на лимите

Первое, что смотреть при «доехал не до конца»: `pos-fb` последней оси. Если он
равен координате одной из операций — программа встала на этой операции, обычно
из-за soft limit. Проверяй **все** точки плана против `MIN_LIMIT/MAX_LIMIT`,
включая склад (его легко унести за ход, передвинув полку).

## 2. MuJoCo (физика)

### Установка и базовые числа

```bash
pip install mujoco            # 4.0.0, CPU достаточно, GPU не нужен
python -c "import mujoco; print(mujoco.__version__)"
```

Замеры на сцене «плита с цапфой — плита с чашкой» (2 тела, 18 геомов):
**37–48 тыс. шагов/с**, результат **детерминирован** при фиксированном шаге.
Полная сборка из 22 деталей при шаге 0,5 мс и программе 5 мин — порядка
10^5–10^6 шагов, то есть минуты, а не часы.

### Чего в MuJoCo нет

1. **Нет примитива «конус»** (`type="cone"` даёт `XML Error: invalid keyword`).
   Цапфу задавай усечённым конусом-мешем (вершины двух окружностей) или
   цилиндром + сферой.
2. **Вогнутую чашку нельзя сделать одним телом**: «плита с отверстием» — это
   solid box, цапфа просто ляжет на его верх. Чашку собирай из примитивов:
   упорное кольцо (диск радиуса внутренней кромки), поясок (вертикальные
   пластины по окружности), раструб (наклонные боксы). Либо SDF-плагин для
   вогнутого меша.
3. **Контакты мягкие**: проникновение конечно. При зазоре 0,26 мм и допуске
   порядка 0,03 мм нужен шаг 0,2–0,5 мс и подбор `solref`/`solimp`;
   наивная сцена даёт 0,25 мм проникновения — это уже больше зазора.

### Порядок работы (не переставлять)

1. **Калибровочный сценарий**: цапфа падает в чашку без смещения. Критерий:
   посадка в номинал ±0,05 мм, проникновение ≤ 0,03 мм. Пока не выполнено —
   двойник измеряет свои артефакты.
2. **Сетка**: смещение 0…4 мм, наклон 0…3°, трение μ 0,2/0,35/0,5, скорость
   подвода. Выход — карта PASS/FAIL и пиковая сила вставки.
3. **Только потом** полный план сборки, исполняемый из `build_plan.json` теми же
   подачами, что в G-коде.

### Модель

- Динамика — только у деталей, которые собираются; станина/витамины статичны.
- Отверстия, не участвующие в посадке, можно не моделировать (массу сохрани —
  плотность или явная масса). Упрощения фиксируй в отчёте.
- Масса: объём × 1,24 г/см³ (PLA), инерция от бокса — достаточно.
- Трение PLA по PLA неизвестно (0,2–0,5): результат — карта по μ, в приёмку
  идёт μ = 0,35 с проверкой краёв.
- Губки — две жёсткие щёки на приводе с трением; «приварить» деталь к захвату
  нельзя, иначе не поймать выскальзывание.

### Приёмка двойника

- все детали на местах, отклонение центра ≤ допуска изделия, наклон ≤ 0,5°;
- максимальное проникновение ≤ 10–12 % зазора (0,03 мм при 0,26 мм);
- в конце 0,5 с покоя конструкция не ползёт, нет контактов выше расчётных;
- пиковая сила вставки ≤ того, что даёт привод;
- повторный запуск даёт тот же результат (фиксируй версию и шаг).

### Отчёт

Формат — как в `cad-demo`: один самодостаточный HTML с вшитым three.js,
таймлайном, графиком сил и таблицей PASS/FAIL. Траектории считаются заранее
(Python), в браузере — только проигрывание. Живой солвер в браузере не нужен.
