# File-log debugging — отладка через file_put_contents в var/tmp

Назначение: временно отладить PHP-поток на dev-сервере, когда нет Xdebug
или не хочется поднимать IDE-сессию. Пишем отладочные строки прямо в код,
деплоим на сервер, смотрим лог, потом **обязательно убираем** перед коммитом.

> Команды на сервере выполнять через скилл **api-dev** — там путь к проекту,
> синтаксис команд (php83), рестарт php-fpm и типовые проблемы.

## Куда писать

Всегда в `var/tmp/` проекта на dev-сервере — эта директория уже в `.gitignore`
(`var/tmp/*`), лог не утечёт в репозиторий.

| Где выполняется код | Путь к логу |
| --- | --- |
| Dev-сервер | `/var/www/api/current/api/var/tmp/<name>_debug.log` |

Путь в коде строить через `getcwd()` или параметр `kernel.project_dir`,
НЕ хардкодить абсолютный путь окружения.

## Правильный паттерн записи

```php
use function date;
use function sprintf;

// в начале метода
file_put_contents(
    getcwd() . '/var/tmp/signup_debug.log',
    sprintf("[%s] %s::%s: %s\n", date('Y-m-d H:i:s'), self::class, __FUNCTION__, 'текст'),
    FILE_APPEND
);
```

Правила строки лога:
- обязательно префикс `[дата-время]` — иначе нельзя понять порядок и время событий
- указывать класс и метод (`self::class`, `__FUNCTION__`)
- писать данные с контекстом: id, email, статус — не «ok»/«fail», а «signup: email=x, confirmed=1»
- `FILE_APPEND` — дописывать в конец, не перезаписывать
- `\n` в конце каждой записи — иначе всё слипнется в одну строку

## Как смотреть лог

Лог пишется на dev-сервере. После деплоя изменённого файла и рестарта php-fpm
(через скилл api-dev) смотреть так:

```bash
tail -f /var/www/api/current/api/var/tmp/signup_debug.log
```

Очистить лог перед новым прогоном:

```bash
> /var/www/api/current/api/var/tmp/signup_debug.log
```

> Симлинк `current` указывает на релиз в `/var/www/api/releases/`. Правки делать
> через путь `current`, но после деплоя следить, что `current` указывает на
> обновлённый релиз (см. api-dev).

## Что отладить — сигналы в логе

- Метод вообще вызывается? → первая строка в начале метода.
- Значения аргументов/состояния до и после вызова → записывать ДО и ПОСЛЕ,
  иначе не увидишь что изменилось.
- Исключение где-то перехвачено и молча съедено? → строка в `catch` перед `throw`.
- Ветка вообще не выполняется? → строка в начале каждой ветки `if/else`.

## Обязательные правила

- **Всегда удалять дебаг-код перед коммитом** — поискать перед коммитом:
  `grep -rn "file_put_contents" src/ tests/`
- После правки файла на сервере **перезапускать php-fpm** (`sudo systemctl restart php83-php-fpm`)
  — иначе opcache отдаёт старый код, лог не появится (см. api-dev).
- Лог создаётся от имени пользователя `apache` — при ошибке создания смотреть
  права: `ls -la /var/www/api/current/api/var/tmp/`.
- `file_put_contents` может вернуть `false` при неверном пути — временно обернуть
  вызов в `var_dump(file_put_contents(...))` на 1 запуск, если лог пуст.
- Не использовать для долгоживущего кода — для этого есть штатный логгер
  (`Psr\Log\LoggerInterface`), file-лог — только временный инструмент.
